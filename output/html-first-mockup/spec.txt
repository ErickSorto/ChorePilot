Family Chore App Mockup Specification — Agent-
Optimized V2
Project Goal
Design a family chore app that feels polished on mobile, tablet, and desktop, follows Material Design 3,
supports  light and dark themes, and is structured so a design agent can generate strong UI without
drifting into documentation boards or vague invented patterns.
The  app  helps  families  stay  in  sync  by:  -  automatically  assigning  chores  each  day  -  showing  who  is
responsible for each chore - allowing users to check chores off - requiring proof when needed - showing
daily, weekly, monthly, and yearly reports - supporting admin and member roles - supporting onboarding,
premium/paywall, notifications, availability modes, and advanced settings
This document is both: 1. a product-facing mockup spec 2. an execution prompt for an AI design agent
working in Figma or via HTML-to-Figma capture
1. Execution Mode
1.1 Core instruction
This is a UI generation task, not a documentation task.
The  agent  must  generate  actual  UI  screens  first.  Do  not create  guide  boards,  report  boards,  spec
summary boards, or abstract planning frames unless this document explicitly asks for them.
1.1.1 Instruction structure rule
Long instructions are acceptable, but for execution-heavy work the agent must process them in this order:
1. Goal — what must be built 2. Constraints — what must not happen 3. Workflow — the order to follow 4.
Quality bar — what “good” looks like 5. Optional preferences — lower-priority refinements
Do not treat all instructions as one flat mixed block. Important requirements must be surfaced as non-
negotiables and actively checked during execution.
1.1.2 Non-negotiable execution block
For this project, the agent should always operate from these core non-negotiables: - Build all screens in
HTML and CSS first - Use AI image generation only for artwork and decorative assets - Verify screens in
browser screenshots before Figma - Then capture into a fresh, organized Figma file - Do not hand-build
1

placeholder vector UI in Figma when a working HTML version already exists - Actively fix visual wonkiness
before capture instead of assuming it will disappear later
1.2 Preferred production workflow
Preferred workflow for this project: 1. Build the milestone boards as local  HTML/CSS screens first using
shared design tokens, shared generated assets, and reusable navigation components. 2. Review the HTML
output visually and fix spacing, clipping, safe-area handling, and density issues before moving anything into
Figma. 3. Capture each board into the target Figma file sequentially. 4. Import each captured board into
Figma as a stable visual frame first. 5. Use Figma tooling only for: - page setup - naming - cleanup -
alignment - moving boards to the correct milestone pages - small refinements outside the captured frame
6. Screenshot-verify each imported board before moving on. 7. Fix clipping, overflow, spacing imbalance,
status bar conflicts, text drift, and blank areas immediately.
1.2.1 HTML-to-Figma capture rules
Final deliverable is the organized Figma file, but HTML/CSS is the primary production surface.
Do not reflow or rebuild working HTML screens in Figma unless there is a specific defect to fix.
Keep milestone labels, board tags, and notes outside the captured product UI.
Preserve the HTML composition as faithfully as possible when moved into Figma.
If text disappears, shifts, clips, or moves off to the side in Figma, treat that as a capture defect and
correct the import method rather than redesigning the screen.
If a milestone board becomes too tall or sparse, split it into multiple frames on the same Figma page
instead of stretching one giant board.
1.2.1.1 Text bounding rules for HTML before capture
This is mandatory because HTML-to-Figma text containers can preserve oversized invisible widths.
Every text element must: - have an explicit max width tied to its actual content container - be wrapped in a
bounded text container before capture - respect the real card or panel width, not just the visual parent
width - be tested in-browser before capture so no text leaves the layout
Text limits: - screen titles: max 2 lines - supporting copy: max 3 lines unless intentionally longer - row titles:
max 1 line unless explicitly wrapped - row captions: max 2 lines
If a parent card looks correct but the underlying text box is wider than the parent, that is a defect and must
be fixed in HTML before import.
1.2.1.2 Screenshot verification rule
The agent must verify each HTML board via screenshots in the browser before Figma capture. If spacing,
clipping, safe areas, text wrapping, or navigation alignment look wrong in screenshots, fix HTML/CSS first.

1.2.2 HTML-first rule
Do not try Figma-first as the primary production path. For this project, HTML/CSS should be treated as the
default generation path because it produces stronger screen composition and more reliable visual output.
1.3 Fallback rule
If any direct raster or image placement path in Figma becomes unreliable, do not keep retrying it. Stay on
the HTML-first workflow and continue using Figma only as the final organization, cleanup, and presentation
layer .
1.4 UI-first rule
The first pass must prioritize: - polished screens - consistent visual density - connected user flows - reusable
art system - accurate Material 3 component behavior
Do not let the first pass drift into: - documentation-style pages - massive notes-only frames - isolated
disconnected screens with no narrative structure

Design for: -  Compact width: under 600dp -  Medium width: 600dp to under 840dp -  Expanded width:

on compact, medium, and expanded.
5.2 Reuse rule for larger layouts
Larger layouts must start from the mobile layout and reuse it intelligently.
That means: - same information architecture - same component logic - same visual language - same screen
purpose - same interaction model where possible
Do not redesign the desktop version into a different product.

5.5 Density rule
Do not leave large empty areas on tablet or desktop boards. If a board has more than roughly 15% unused
space on the right or bottom: - reduce the board size, or - add the missing companion pane, chart panel,
detail panel, or next flow step
5.6 Safe area rule
All board titles, headers, and labels must stay inside safe bounds with at least 32px outer padding. No text
may be clipped by board edges.
5.7 Crop rule
Crop every board to content bounds plus consistent outer padding. Do not leave a large empty lower half
under the final row.

7. Theme System
Provide both light and dark themes.
The mockup must clearly show: - semantic Material color roles - typography system - component inventory -
elevation usage - icon style - illustration direction - light vs dark QA comparisons
7.1 Theme consistency rule
Build the light theme first. Derive dark theme by swapping semantic tokens, not by redesigning the UI.
Light  and  dark  must  reuse:  -  the  same  component  anatomy  -  the  same  spacing  system  -  the  same
illustration family - the same icon set - the same information hierarchy
Do not create unrelated dark-only layouts.
7.2 Theme separation rule
Light and dark themes must be shown in clearly separated frame groups or page regions. Do not place
them interleaved in the same main visual lane.
Required rules: - light theme boards live in one clearly labeled group - dark theme boards live in a separate
clearly labeled group - the design stays exactly the same between themes - only colors, surfaces, shadows,
and semantic tokens change - do not mix dark and light components in one implementation lane - do not
let the next agent infer hybrid layouts from mixed boards

10.3 Art direction
Use exportable illustrations with a soft, warm, family-safe, Material-friendly look.
Core onboarding art style
The onboarding should feel emotionally engaging, premium, and welcoming. It should not feel like a plain
setup wizard.
Visual style: - soft-gradient illustration system with rounded forms - warm household scenes and human
moments - polished editorial composition, not generic app clipart - subtle depth through layered shapes,
soft shadows, and light atmospheric glow - expressive but calm color accents drawn from the app theme -
friendly  faces  and  family  interactions  without  over-detailed  realism  -  clean  silhouettes  and  simplified
features for consistency - no uncanny realism - no dark gritty mood - no noisy collage look - no mixed
illustration styles
Engagement principles for onboarding art
Every major onboarding screen should feel like part of one emotional journey. The visual progression
should move from: 1. welcome and hope 2. recognition of the household problem 3. personalization and
being understood 4. confidence in the plan 5. commitment to premium
That means the art should evolve across the onboarding screens: - opening screens should feel warm,
inviting, and aspirational - middle screens should feel reflective and specific to the household’s pain points -
snapshot and roadmap screens should feel intelligent, structured, and rewarding - paywall handoff should
feel premium, calm, and high-trust
Onboarding screen composition style
For  onboarding  screens,  use  this  structure  unless  a  specific  screen  needs  a  justified  variation:  -  small
progress indicator at the top - one main prompt or question per screen - one focal visual area in the upper
third or upper half - one primary interaction area in the middle - one strong CTA area at the bottom -
minimal secondary actions
Do not make onboarding feel like a long form. Each screen should feel intentionally composed and easy to
emotionally process.
